# Chapter 2: Background and Related Work

## 2.1 The HTML5 Parsing Specification
The parsing of HTML has historically been one of the most contentious areas in compiler engineering. Before the publication of the W3C HTML5 Recommendation (2014) and the WHATWG Living Standard, web browsers implemented ad-hoc, proprietary error-recovery heuristics. This created the infamous "tag soup" phenomenon, where identical HTML markup yielded radically divergent Document Object Models (DOMs) across different rendering engines.

To resolve this ambiguity, the WHATWG specification defined HTML parsing not as a formal grammar, but as a dual-phase state machine:
1. **Tokenization Phase:** An 80+ state automaton converting a raw stream of Unicode characters into typed tokens: `DOCTYPE`, `StartTag`, `EndTag`, `Comment`, `Character`, and `EndOfFile`.
2. **Tree Construction Phase:** A state-driven tree builder maintaining two primary stacks:
   - **Stack of Open Elements:** Maintains the current ancestral hierarchy.
   - **List of Active Formatting Elements:** Tracks inline formatting tags (`<b>`, `<i>`, `<a>`) to implement the complex **Adoption Agency Algorithm (AAA)** (§13.2.6.4.7) when tags are misnested.

A critical design requirement of HTML5 is **graceful recovery**: an HTML parser is explicitly prohibited from throwing fatal parsing exceptions on ill-formed input. Every conceivable syntax error must be resolved deterministically into a well-formed tree.

## 2.2 LLMs in Automated Software Engineering
Early applications of Large Language Models (LLMs) to software synthesis treated program generation as a next-token prediction problem over code repositories. While effective for localized functions (e.g., HumanEval, MBPP), monolithic code generation exhibits steep failure rates on complex system components.

Benchmarks such as **SWE-bench** (Jimenez et al., 2024) demonstrated that frontier models often fail to resolve real-world software engineering issues when presented with monolithic prompts. Key failure modes include:
* Overconfidence in generated syntax.
* Introduction of subtle logic inversions in state transitions.
* Inability to verify conformance against multi-stage contracts.

## 2.3 Multi-Agent Orchestration & Communicative Architectures
To address the shortcomings of monolithic generation, recent research has explored multi-agent collaboration:
* **MetaGPT** (Hong et al., 2023) introduced Standardized Operating Procedures (SOPs) into agent workflows, assigning distinct roles (Product Manager, Architect, Engineer, QA).
* **ChatDev** (Qian et al., 2023) explored communicative agent chat chains for rapid application prototyping.
* **Reflexion** (Shinn et al., 2023) demonstrated that verbal reinforcement learning—allowing agents to reflect on execution failure logs—significantly improves code synthesis accuracy.

This thesis builds upon these foundations by introducing a **partially ordered assembly line** specifically engineered for compiler components, enforcing intermediate file artifacts and concurrent review gating.

## 2.4 Program Repair & Automated Debugging
Automated Program Repair (APR) has historically utilized genetic programming or search-based template matching. In the LLM era, **Demystifying GPT Self-Repair for Code Generation** (Olausson et al., 2023) highlighted that while LLMs can repair simple syntax errors, they frequently diverge into circular failure loops without rich feedback.

Our work addresses this limitation by feeding the `RepairAgentAI` structured runtime telemetry: rather than generic error messages, the agent receives character-level token states, current tree depth, and AST difference trees generated by `MonitorAgentAI`.

## 2.5 Differential Testing & Oracle Verification
Because HTML5 tree construction rules are immensely complex, establishing correctness requires robust testing oracles. **Differential Testing** (McKeeman, 1998) provides an ideal verification framework: feeding identical input documents into multiple independent implementations and comparing their resulting AST representations.

In this project, differential testing is embedded directly into the developer workflow: `BeautifulSoup4` acts as a live differential oracle within the interactive Quality Dashboard (`scripts/serve_dashboard.py`), highlighting semantic discrepancies in real time.
